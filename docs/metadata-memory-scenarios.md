# Metadata memory scenarios

The opt-in [runtime calibration tool](runtime-calibration.md) records the declarations
used by this scenario and separates observed throughput from assumptions.

`plan MODEL --facts snapshot.json --json` adds `metadata_plan` to the schema-1 plan envelope while retaining the existing heuristic quantization plans and numerical scoring. The input is a schema-1 `model_facts` snapshot, or the `model_facts` field of a schema-1 runtime calibration report. Exact model name and full Ollama digest must match. Inputs are bounded to 64 KiB and finite JSON. Saved declarations are not revalidated against a live runtime by this command.

Snapshots distinguish runtime-reported architecture, supported context, quantization, capabilities, disk size and dimensions from derived head dimensions. A head dimension can be derived only by exact embedding-length / attention-head-count division when the explicit field is absent; invalid explicit fields remain unknown. The source observation/version is retained by the snapshot. [Ollama show](https://docs.ollama.com/api-reference/show-model-details) supplies model declarations; [tags](https://docs.ollama.com/api/tags) supplies the local model digest and disk-size declaration. A digest identifies the runtime model, not an HF file/repository commit or usage permission.

This first scenario supports the standard full-attention `llama` layout only. Unknown/missing dimensions, other architectures, sliding-window/shared-KV/expert layouts and requested context above declared support return explicit non-estimated statuses. Unknown supported context stays unknown. There is no fallback that treats an unsupported cache as ordinary Llama attention. See [HF cache strategies](https://huggingface.co/docs/transformers/kv_cache) for why different cache layouts need distinct treatment.

For this layout, the scenario uses `layers * KV heads * (key head dimension + value head dimension) * requested context * concurrent requests * bytes per cache element`. FP16 uses two bytes and FP32 four; quantized caches are unsupported. It assumes uniform per-layer dimensions, full requested-context occupancy and one shared resident weight copy. Disk size is an explicitly labeled weight-memory proxy, not measured tensor residency. Concurrent requests multiply cache, not the shared weight proxy.

`--concurrency` (1–16), `--gpu-weight-percent` (0–100), `--kv-type` (`fp16`/`fp32`), `--kv-device` (`gpu`/`cpu`) and `--overhead-mib` (0–4096, default 256) describe assumptions. Weight split, cache placement and overhead placement are explicit; overhead follows the selected cache device. Nondefault scenario options require `--facts`. Estimates expose components and separate CPU/GPU byte totals. They do not measure allocator padding, scratch buffers, runtime partitioning, actual offload, compression, unified-memory overlap or support at the requested context.

The old plan remains a separate model-name heuristic and does not become authoritative because a metadata scenario is present. Neither scenario validates inference speed or quality. Regression fixtures establish calculation/contract behavior; they are not real model measurements. The installed-package matrix exercises saved-facts planning outside the checkout.
